## [Не выпущено] — 0.2.0.dev0

### Добавлено
- **Проектная документация** `docs/blueprint/00–16`: домен и роли, сценарии С1–С5, модули, матрица прав,
  архитектура, офлайн-матрица, настройки, макеты, сравнение технологий, план и риски, трассировка R-01..R-46,
  журнал решений, защищённая выдача КП, NanoCAD.
- **Контракты** `contracts/`: каталог команд v2 (22 команды, офлайн-классы), права v2 (12 ролей, роли в проекте),
  переходы статусов, денежные тест-векторы.
- **Эталонное ядро** `spikes/reference-core` — исполняемая спецификация инвариантов среза 1 (36 тестов).
- **Сервер** (Starlette + SQLAlchemy 2; PostgreSQL, MS SQL, SQLite для тестов/пилота):
  заказчики, тендеры, ТКП, явное начало РКД, проект, команда проекта, комплекты; учётные записи, роли
  с историей выдач, блокировки, сеансы; аудит только на добавление; API `/api/v1`; CLI `vector-server`.
- **Резервное копирование**: зашифрованный формат `.vbak`, проверка, ротация, восстановление в пустую БД любой СУБД.
- **Клиент** (PySide6/QML): офлайн-очередь с устойчивыми id операций, обнаружение конфликтов, зашифрованный
  локальный кэш, офлайн-вход; все экраны среза в светлой и тёмной теме.
- **UI-тесты** на настоящем QML (offscreen) и стенд скриншотов `tools/ui_harness.py`; скриншоты в `docs/screenshots`.
- Пример конфигурации сервера с комментариями `config/vector-server.example.toml`.
- `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, этот файл.

- **Задачи проекта** (сервер): создание, правка, статусы «Открыта → В работе → Выполнена», отмена и повторное
  открытие с причиной; исполнитель — только участник команды проекта; ссылка задачи на документ.
- **Документы с версиями** (сервер): карточка с обозначением, неизменяемые версии файлов (SHA-256, размер, триггеры
  на всех СУБД), загрузка и скачивание `/api/v1/files` с проверкой хэша в обе стороны, квитанции загрузки,
  обнаружение порчи файла при скачивании, аудит загрузок и скачиваний. Файлы входят в резервную копию (D-20).
- Схема БД v3 (до первой эксплуатации миграций нет — схема создаётся заново).
- **Задачи и документы в клиенте**: задачи и карточки документов работают без связи (очередь), новая версия
  файла — только онлайн; скачивание с проверкой SHA-256 и атомарной записью, повреждённый файл не сохраняется.
- **Интерфейс комплекта**: на странице проекта выбор комплекта показывает задачи (переходы статусов с причиной,
  исполнитель, срок, документ) и документы (версии, загрузка новой версии, скачивание); объяснение недоступности
  в офлайне — баннером и текстом, а не всплывающей подсказкой. Скриншоты `*-09`, `*-10`.
- Параметр `max_file_mb` в примере конфигурации.
- **Документация по эксплуатации** `docs/ops/`: установка (PostgreSQL, MS SQL, TLS, секреты, systemd, клиент),
  резервное копирование и восстановление (ключ, расписание, 3-2-1, коды ошибок), регламент учебного
  восстановления с журналом. Шаги, выполненные в песочнице, помечены ✅, непроверенные на платформе — 🟡.
- Юниты systemd `deploy/systemd/`: служба сервера с ограничениями и ежедневная копия по таймеру.

### Исправлено
- Текст главной кнопки был чёрным (свойство темы `onPrimary` трактовалось QML как обработчик сигнала).
- Иконки и поле поиска не соблюдали размер/стиль; выбор объекта при переходе из другого раздела не работал;
  пункты меню по правам появлялись не всегда; длинный статус сжимал название; история показывала внутренние коды.
- Эталонное ядро не запускалось после расширения каталога команд до v2 (D-17).
- **Аварийное завершение клиента** после нескольких тысяч сигналов: ошибка счётчика ссылок в PySide6 6.12.0.
  Зависимость ограничена `>=6.11.3,<6.12`, добавлен страж `tests/client/test_qt_binding_refcounts.py`;
  данные для QML дополнительно очищаются от `None` (`qml_safe`) (D-21).
- В журнале загрузок/скачиваний файлов не записывалось основание доступа; в истории показывался код `file.upload`.
- **Память при резервном копировании не зависит от объёма файлов** (issue #8):
  таблицы читаются потоком (на PostgreSQL — серверным курсором), копия расшифровывается и распаковывается
  на лету, пачка вставки при восстановлении ограничена ~4 МБ. Замер на 150 МБ файлов (PostgreSQL):
  копирование +257 МБ → +4 МБ пиковой памяти, проверка копии ≈ 0 МБ, восстановление со сверкой +12 МБ.
- **Загрузка и скачивание файлов документов — потоком** (issue #8): раньше файл целиком держался в памяти
  сервера и клиента (до `max_file_mb` × несколько копий на каждую передачу). Теперь блоки по 1 МБ идут через
  временный файл; замер на файле 150 МБ через настоящий HTTP-сервер — пиковая память +0 МБ (контроль +110…145 МБ).
  Посторонний и слишком большой файл (по `Content-Length`) получают отказ до приёма тела; файл, изменившийся
  во время загрузки, не записывается; повреждённый файл не отдаётся ни байтом; обрыв скачивания не оставляет
  на клиенте ни целевого, ни частичного файла. Сохранённый файл и запись каталога сбрасываются на диск (fsync).
  Потеря ответа на загрузке или при создании версии → повтор даёт ровно одну версию и одно содержимое (тест).
- Понятное сообщение при неверном/повреждённом файле ключа резервных копий (раньше «Incorrect padding»).
- Ротация копий удаляла **любые** `*.vbak` в каталоге по времени файла, включая сделанные вручную под своим
  именем; теперь — только автоматические `vector-ГГГГММДДTччммссZ.vbak`, по метке времени в имени.

### Безопасность
- Строка подключения к БД не может храниться в конфигурации; закрытый ключ TLS и файл строки подключения
  должны иметь права только для службы; пароль администратора не принимается из командной строки.
