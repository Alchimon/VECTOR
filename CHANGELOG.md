### Добавлено (2026-11-16 — 2026-11-24, D-56…D-79)
- **Пополнение расходников по порогу (С4 шаг 7, D-79, issue #12):** склад задаёт правило «ниже порога — пополнить
  до» для пары склад+позиция с карточки позиции (порогов и количеств по умолчанию нет — Q2). Когда доступное
  опускается ниже порога, система создаёт черновую позицию пополнения (или обновляет её количество — одна
  открытая на пару); при восстановлении остатка выше порога открытый черновик закрывается сам («остаток
  восстановлен»). Черновик подтверждают обе стороны — склад и закупка (по одному разу, только при связи);
  отклонить может любая с причиной. Отключение правила не удаляет историю черновиков. Схема v43
  (stock_replenishment_rules, stock_replenishment_drafts), команды stock.replen_rule_set / _update /
  stock.replen_confirm / stock.replen_dismiss, вкладка «Пополнение» на странице «Склад».
- **Предложение перемещения между проектами и совместное решение «склад + закупка» (С4 шаги 3–4, D-78, issue #12):**
  закупка или участник проекта предлагает переместить позицию из резерва другого проекта (или из свободного
  остатка) в свой проект — кнопка «Предложить перемещение» в строке потребности (работает без связи, в очередь).
  Предложение — не резерв, не заказ и не движение: оно ждёт решения на вкладке «Предложения» страницы «Склад».
  Решение одно и только при связи: склад «перебрасывает резерв» (резервы донора снимаются старшие-сначала,
  частичное снятие уменьшает резерв, недостающее берётся из свободного, резерв получателя создаётся в той же
  транзакции с проверкой покрытия строки потребности), закупка решает «закупим» (сам заказ создаётся отдельно),
  любая из сторон отказывает с причиной; автор отзывает предложение до решения (причина обязательна). Автор и
  вторая сторона получают уведомления; видят предложения склад, закупка и участники затронутых проектов.
  Схема v42 (таблица stock_transfer_proposals), команды proposal.propose / proposal.withdraw / proposal.decide.
- **Корректировка остатка с подписью руководителя отдела (С4, D-77, issue #12):** склад создаёт корректировку с
  карточки позиции (склад, фактический остаток по пересчёту, основание-акт — обязательно); в учёт она попадает
  только после подписи руководителя отдела (четыре глаза) тем же способом, что акты склада (настройка
  stock.act_signature). Подпись проводит движение журнала на разницу с источником «Корректировка (подписал …)» и
  пишет подпись с контрольной суммой содержания. Предохранители: остаток не должен «уплыть» с момента создания
  (иначе создают заново) и факт не ниже активных резервов; по паре склад+позиция — одна ждущая подписи
  корректировка. Неподписанную отменяет автор с причиной; подписанную исправляют новой корректировкой.
  Руководители отдела получают уведомление «ждёт подписи», автор — «подписана». Схема v41 (таблица
  stock_adjustments), команды stock.adjust / stock.adjust_sign / stock.adjust_cancel (только при связи), вкладка
  «Корректировки» на странице «Склад».
- **Обмен расчётом комплекта с Excel — файлы .xlsx (R-31, issue #11):** в редакторе позиций «Импорт из .xlsx…» /
  «Экспорт в .xlsx…» (работают без связи). Числа — десятичным текстом, без float; значения длиннее 15 значащих
  цифр выгружаются текстовыми ячейками (предел точности Excel), а при импорте такая числовая ячейка — замечание
  excel_precision (Excel её уже исказил). Запись файла атомарна (временный файл + fsync + replace — обрезанного
  .xlsx не бывает), импорт — «всё или ничего» с предпросмотром: замечания с номерами строк листа, позиции
  добавляются только после подтверждения. Чтение/запись OOXML — своим минимальным кодом (core/xlsx.py),
  новых зависимостей нет.
- **Сквозные процессы проекта (blueprint 52, этапы 2–5, D-56…D-61):** шесть потоков со шлюзами и журналом событий,
  риск-разрешения РП с причиной и сроком, лиды с конвертацией в тендер; ревизии РКД с внешним шифром по профилю
  заказчика, внутренняя проверка, замечания/ответы к точной ревизии, неизменяемый трансмиттал с ZIP-пакетом и
  доказуемым SHA-256; закупочная консолидация (группы, пакеты, allocation) без двойного покрытия; снимок
  готовности сборки для нарядов.
- **ПНР, приёмочные испытания и доставка (этап 6, D-66…D-70):** настраиваемые шаблоны чек-листов (разделы и
  градации — снимком в сессии), запросы ПНР, FAT-сессии с замечаниями «к проекту, не к человеку» и шлюзом
  отгрузки (последний финальный FAT — успешный и без открытых блокирующих замечаний); формы документов доставки
  с плейсхолдерами и рендером-снимком; клиентский блок «ПНР, испытания и доставка» на карточке проекта.
- **Архив и аналитика (этап 7, D-71…D-73):** снимок закрытия проекта с агрегированными фактами; аналитика проекта
  и сводная аналитика портфеля — только чтение из снимка, без денег и персональных данных.
- **ТК РФ-контур сверхурочной работы (blueprint 51, D-74):** основания привлечения — закрытый справочник по
  ст. 99/113 ТК РФ; кадровые категории (запрещающие и «только с согласия») назначает администратор, проверка —
  при подаче заявки и повторно при решении руководителя; лимит «4 часа за два дня подряд» (ст. 99 ч. 6).
- **Норма учётного периода (D-75):** границы и норма текущего периода по производственному календарю РФ
  (40 ч/неделя; предпраздничный день короче на час) — в снимке pull, в интерфейсе и внутри неизменяемого
  снимка закрытой ведомости; год без календаря делает норму честно «неполной», а не угаданной.
- **Подготовка пилота (D-76):** демо-данные стенда для всех новых контуров; самопроверка стенда — разделы 16–19
  (чек-лист владельца П-25…П-28 в `docs/ops/test-pc.md`); план пилота с критериями успеха — `docs/ops/pilot.md`;
  сквозная проверка пакета «архив ветки → установка в пустой каталог → самопроверка» и учебное восстановление
  из копии — зелёные на Linux.
- **Встроенное руководство пользователя (issue #2, справочный центр):** раздел «Справка» (F1) получил вкладку

### Исправлено (2026-11-24)
- **Карточка наряда:** риск-разрешения из снимка готовности сборки (D-61) не отображались — ветка форматирования
  использовала `_date_ru` без импорта и упала бы с `NameError` на любом наряде, выпущенном по риск-разрешению;
  добавлен регрессионный тест представления (найдено линтером, F821).
- **Подсказки:** кнопки «Новая ревизия» (ревизия документа, РКД) и «Новая ревизия ТП» (техпроцесс) имеют одинаковый
  текст — в словаре подсказок вторая запись затирала первую, и кнопка РКД показывала чужую подсказку с неверным
  «можно без связи» (кнопка требует связь). Кнопка техпроцесса переименована в «Новая ревизия ТП» — как её диалог
  (найдено линтером, F601).
- **Эталонное ядро спайка (spikes/reference-core):** его fail-closed проверка «каждая команда каталога либо
  исполнена в спайке, либо явно вне его области» молча сгнила — срез 1 не пополнялся с этапа 2, и набор из 36
  тестов падал на старте (122 команды D-20…D-76 без отметки). Перечень «вне области» пополнен; в основной набор
  добавлен страж (`tests/core/test_spike_reference_core.py`), который падает при разъезде каталога и спайка;
  полный набор спайка (`python -m unittest`, 36 тестов) снова зелёный.
- **Линтер (ruff, классы F и E9):** удалены неиспользуемые импорты и мёртвые переменные (`can_propose`/`can_decide`
  в представлении производства — флаги считает `norm_proposals_view`), восстановлен импорт `Any` в `core/rkd.py`,
  явная инициализация счётчика строк в `backup.verify_backup`.
- **Робастность (ruff B905):** все `zip()` — со `strict=True`: несовпадение длин (например, повреждённая запись
  резервной копии с меньшим числом значений, чем колонок) теперь громкая ошибка, а не тихо пропущенная колонка;
  security-линт (ruff S) разобран — существующие меры защиты аннотированы `noqa` с пояснениями (XML-календарь без
  DOCTYPE/ENTITY, имена таблиц из схемы, 0.0.0.0 для ЛВС с TLS).
- **Аудит зависимостей (pip-audit, 2026-11-24):** продуктовые зависимости (по `constraints.txt`) без известных
  уязвимостей; находки касались только setuptools песочницы разработки — обновлён. Практика записана в SECURITY.md.

### Изменено

### Добавлено
- **Архитектурный blueprint сквозного исполнения проекта:** спроектированы независимые потоки, риск-переходы с ответственностью РП, workflow ревизий/замечаний/трансмитталов, сводные закупки и allocation по комплектам, readiness/FAT/площадка, UI без редизайна и этапы реализации. Не изображает отсутствующую функциональность как готовую; см. `docs/blueprint/52-project-delivery-workflows.md`.
- **Предварительные правовые лимиты сверхурочной работы (D-55):** ожидающие заявки резервируют ёмкость; сервер запрещает более 4 часов в календарный день и более консервативных 120 часов сверхурочной работы в календарный год. Выходные и праздничные часы учитываются отдельными категориями. Нет поддержки исключений, 240-часового лимита и кадровых согласий — правовая проверка остаётся обязательной.
- **Закрытие ведомости часов вне графика (D-54):** администратор закрывает период сотрудника снимком одобренных заявок; ожидающие решения блокируют закрытие. Хэш SHA-256 подтверждает содержимое. Исправления — только новой связанной ревизией и с причиной; интерфейс показывает историю ревизий. Это не полный юридический табель и не расчёт/выгрузка оплаты в 1С.
- **Недельные сводки подразделений (D-50, начальный срез):** руководителю доступны за прошлую полную неделю число отправленных дневных отчётов и суммарные часы по его подразделению с включением вложенных подразделений. На дашборде нет имён сотрудников и данных о нажатиях/использованных программах; это агрегированная рабочая метрика, не табель и не слежение.
- **Проектная документация** `docs/blueprint/00–16`: домен и роли, сценарии С1–С5, модули, матрица прав,
  архитектура, офлайн-матрица, настройки, макеты, сравнение технологий, план и риски, трассировка R-01..R-46,
  журнал решений, защищённая выдача КП, NanoCAD.

  переходы статусов, денежные тест-векторы.

  заказчики, тендеры, ТКП, явное начало РКД, проект, команда проекта, комплекты; учётные записи, роли

### Безопасность
- **Пароли больше не входят в контрольную сумму запроса** (`operations.request_hash`). Раньше для смены и сброса
  пароля и создания пользователя сумма SHA-256 без соли считалась вместе с паролем — по копии БД пароль можно было
  подобрать в обход Argon2id. Теперь поля из `vector.core.redact.SECRET_FIELDS` исключаются; повтор операции с тем же
  id возвращает сохранённый итог. Старые записи зачищает новая команда `vector-server redact-secrets [--apply]`.
  Клиент при потере ответа не хранит пароль в очереди. Тест следит, чтобы каждое новое поле с паролем попало в список.
- Пароль подписи акта проверяется сервером; неверные попытки ограничены отдельным счётчиком (только неудачи).
- Файлы резервных копий (`.vbak`, в т. ч. копии до миграции) создаются с правами только владельца (0600).
- Строка подключения к БД не может храниться в конфигурации; закрытый ключ TLS и файл строки подключения
  должны иметь права только для службы; пароль администратора не принимается из командной строки.
