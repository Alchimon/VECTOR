- **Замещение ролей, руководитель отдела в согласовании, гарантии расчёта НДС (D-34, ответы владельца A-37…A-39).**
  Замещение (`delegation.create` / `delegation.revoke`, только онлайн): глобальная роль передаётся на срок (до 366
  дней) с причиной; свою — носитель, за отсутствующего — руководитель отдела или администратор
  (`delegation.manage`, не себе); «Администратор» не передаётся; без цепочек; замещение приостанавливается, если у
  носителя отозвали роль. Каждое решение (согласование заказа и ТКП) хранит неизменяемое основание — кто, какой
  ролью, за кого (`approval_bases`); в истории «замещает …». Руководитель отдела видит заказы, цены и согласования
  и может согласовать сам (резерв). Покрытие ролей (`role_coverage` в pull): роли «ни у кого / у одного человека».
  НДС: двойной расчёт (точные дроби против Decimal) и тождества по строкам, итогам и ставкам — не сошлось, суммы не
  показываются и заказ не отправить (`calc_check_failed`); суммы из счёта поставщика в заказе и сверка до копейки,
  расхождение — отправка только с причиной (`invoice_reason_required`), результат сверки неизменяем; предупреждение

- **Память при резервном копировании не зависит от объёма файлов** (issue #8):
  таблицы читаются потоком (на PostgreSQL — серверным курсором), копия расшифровывается и распаковывается
  на лету, пачка вставки при восстановлении ограничена ~4 МБ. Замер на 150 МБ файлов (PostgreSQL):
  копирование +257 МБ → +4 МБ пиковой памяти, проверка копии ≈ 0 МБ, восстановление со сверкой +12 МБ.
- **Загрузка и скачивание файлов документов — потоком** (issue #8): раньше файл целиком держался в памяти
  сервера и клиента (до `max_file_mb` × несколько копий на каждую передачу). Теперь блоки по 1 МБ идут через
  временный файл; замер на файле 150 МБ через настоящий HTTP-сервер — пиковая память +0 МБ (контроль +110…145 МБ).
  Посторонний и слишком большой файл (по `Content-Length`) получают отказ до приёма тела; файл, изменившийся
  во время загрузки, не записывается; повреждённый файл не отдаётся ни байтом; обрыв скачивания не оставляет
  на клиенте ни целевого, ни частичного файла. Сохранённый файл и запись каталога сбрасываются на диск (fsync).
  Потеря ответа на загрузке или при создании версии → повтор даёт ровно одну версию и одно содержимое (тест).

### Безопасность
- **Пароли больше не входят в контрольную сумму запроса** (`operations.request_hash`). Раньше для смены и сброса
  пароля и создания пользователя сумма SHA-256 без соли считалась вместе с паролем — по копии БД пароль можно было
  подобрать в обход Argon2id. Теперь поля из `vector.core.redact.SECRET_FIELDS` исключаются; повтор операции с тем же
  id возвращает сохранённый итог. Старые записи зачищает новая команда `vector-server redact-secrets [--apply]`.
  Клиент при потере ответа не хранит пароль в очереди. Тест следит, чтобы каждое новое поле с паролем попало в список.
- Пароль подписи акта проверяется сервером; неверные попытки ограничены отдельным счётчиком (только неудачи).
- Файлы резервных копий (`.vbak`, в т. ч. копии до миграции) создаются с правами только владельца (0600).
- Строка подключения к БД не может храниться в конфигурации; закрытый ключ TLS и файл строки подключения
  должны иметь права только для службы; пароль администратора не принимается из командной строки.
