# 57 — P3: база знаний компании, @упоминания и комментарии, эстафета отделов, внутренние ссылки

> Статус: **утверждён владельцем** (порядок P3-1 → P3-4). P3-1 (внутренние ссылки) и P3-2 (комментарии + @упоминания + уведомления) — реализованы.
> Затрагивает сервер (новые таблицы и команды), клиент (оболочка 2.0), синхронизацию и лицензирование.

## 0. Принципы (общие для всех четырёх частей)

1. **Оффлайн-первый, как везде в ВЕКТОР**: создание комментария/записи базы знаний — команда с очередью
   («можно без связи»), чтение — из локального кэша (pull). Решения принимает сервер.
2. **Согласованность с существующим**: команды регистрируются в contracts (permissions), снапшоты — в pull
   (новые stock-коллекции), уведомления — через существующий `notifications` + NotificationsPage, права — через
   роли (глобальные и проектные), аудит — через существующий журнал команд.
3. **Лицензирование**: база знаний и комментарии — модуль `pdm` (ядро работы с проектами); обмен эстафетой —
   `pdm` + участвующие модули по месту (supply/production). Новых платных модулей не вводим.
4. **Ничего не ломаем**: новые таблицы — отдельные, существующие миграции не трогаем; новые коллекции pull —
   добавочные (старые клиенты их игнорируют).

## 1. Проектная база знаний + база данных компании

**Состав**: стандарты организации (СТО), шаблоны (уже есть `office_doc` с `is_template` — расширяем), справочник
оборудования и подрядчиков, привязка записей к проекту или к компании в целом.

### Модель данных (сервер)

| Таблица | Поля (ключевые) | Примечание |
|---|---|---|
| `kb_articles` | id, scope (`company`/`project`), project_id?, kind (`standard`/`template_ref`/`note`/`howto`), code, title, body_md, tags[], version, updated_by/at | статья базы знаний; code человекочитаемый («СТО-01») |
| `vendors` | id, inn, name, contacts_json, kind (`supplier`/`contractor`/`both`), status (`active`/`archive`), rating_note | справочник подрядчиков/поставщиков компании (не путать со `suppliers` закупки — тот про конкретные заказы; здесь — общая база с возможностью ссылки из закупки) |
| `equipment_catalog` | id, code, name, category, params_json (паспортные характеристики), manufacturer, source_doc_id? | справочник оборудования для подстановки в спецификации (Ф1: позиция спецификации может ссылаться на запись каталога) |

Все три — версионные (`version` + optimistic concurrency, как у документов) и попадают в аудит.

### Команды (contracts: `kb.*`, `vendor.*`, `equipment.*`)

- `kb.create / kb.update / kb.archive` — offline-capable (создание заметки без связи допустимо).
- `vendor.create / vendor.update / vendor.archive` — online (справочник компании правят ответственные; редко).
- `equipment.create / equipment.update / equipment.archive` — online.
- Чтение — pull: новые stock-коллекции `kb_articles`, `vendors`, `equipment` (по правам чтения модуля pdm).

### Клиент

- Новый раздел «Знания» (рельса 2.0): список статей с тегами/поиском, просмотр/редактор markdown, вкладки
  «Справочники» (подрядчики, оборудование) — master-detail, тот же MasterDetail/InspectorPane2.
- **Ctrl+K**: палитра команд (`CommandPalette2`) расширяется источником «база знаний и справочники»: поиск по
  title/code/tags статей и по name/inn подрядчиков; выбор — открывает статью/карточку во вкладке.
- Поиск — локальный по кэшу (работает без связи), ранжирование: точное совпадение кода → заголовок → теги → текст.

## 2. @упоминания и комментарии с уведомлениями

Сейчас «Обсуждение» документа (D-118) показывает замечания ревизий РКД — узко. Обобщаем:

### Модель данных

| Таблица | Поля | Примечание |
|---|---|---|
| `comments` | id, object_type (`document`/`task`/`kit`/`project`), object_id, parent_id? (тред), author_id, body_md, mentions_json[], created_at, edited_at?, deleted_at? | мягкое удаление (deleted_at), чтобы треды не разваливались |

- **Парсинг упоминаний**: при принятии команды сервер извлекает `@login` из body_md, проверяет существование
  пользователя и его доступ к объекту; `mentions_json` — подтверждённые упоминания.
- **Уведомления**: для каждого подтверждённого упомянутого — запись в существующий `notifications`
  («Вас упомянули в обсуждении Д-15», переход — открывает объект и подсвечивает комментарий). Ответ в треде
  уведомляет автора родительского комментария (без @).
- **Команды**: `comment.add` (offline-capable, очередь), `comment.edit` (только автор, 24 ч), `comment.delete`
  (автор или руководитель проекта). Чтение — pull-коллекция `comments` (по видимым пользователю объектам).

### Клиент

- Вкладка «Обсуждение» инспектора (InspectorPane2) — уже есть; переключается на `comments` (треды, ответы,
  ввод с автодополнением `@` по участникам проекта/оргструктуре из кэша `org_members`).
- Уведомление → открытие объекта с якорем комментария (object_tabs + подсветка).

## 3. Передача эстафеты между отделами (АСУ ТП → Снабжение → Производство)

**Суть**: комплект/заказ явно «переходит» между подразделениями с чек-листом готовности; видно, у кого объект
сейчас и что блокирует передачу.

### Модель данных

| Таблица | Поля | Примечание |
|---|---|---|
| `handover_routes` | id, object_type (`kit`/`purchase_order`), object_id, steps_json [{unit_id, order, checklist_template_id}], active | маршрут по подразделениям; шаблоны маршрутов — в настройках компании |
| `handover_steps` | id, route_id, unit_id, state (`pending`/`active`/`done`/`returned`), checklist_json [{item, done, by, at}], started_at, done_at, note | текущий шаг = `active`; «returned» — возврат с комментарием (блокер) |
| `checklist_templates` | id, unit_kind, items_json[] | шаблоны чек-листов («схема утверждена», «спецификация заморожена»…) |

- **Команды**: `handover.start` (маршрут на объект), `handover.advance` (шаг выполнен — все пункты чек-листа
  отмечены; сервер проверяет), `handover.return` (возврат с причиной), `handover.check` (отметка пункта).
  Все — online (согласование между подразделениями требует актуального состояния), кроме `handover.check`
  (можно без связи).
- **Права**: отметить пункт/завершить шаг — участник соответствующего подразделения (org_members) с ролью в
  проекте; старт маршрута — РП/ГИП.
- **Уведомления**: при переходе шага — уведомление руководителю следующего подразделения («Комплект АТХ передан
  в Снабжение: 3 пункта чек-листа закрыты»); при возврате — автору предыдущего шага с причиной.

### Клиент

- Полоса эстафеты в карточке комплекта/заказа (инспектор + вкладка): шаги-чипы «АСУ ТП ✓ → Снабжение ● →
  Производство ○», текущий шаг раскрыт чек-листом с отметками; кнопки «Передать дальше»/«Вернуть» по правам.
- Виджет «У меня на приёмке» на «Главной» (HomePage2): активные шаги моих подразделений.

## 4. Внутренние ссылки на объекты

- **Формат**: `vector://project/<id>`, `vector://kit/<id>`, `vector://document/<id>`, `vector://kb/<id>`,
  `vector://task/<id>` — текстовая ссылка, не зависящая от имени хоста.
- **Копирование**: в уже введённые контекстные меню (вкладки, дерево проектов, карточки документов/задач,
  статьи знаний) добавляется пункт «Копировать ссылку» (backend.copyText).
- **Вставка/переход**: палитра Ctrl+K принимает ссылку целиком → `openObject`; поле поиска справки — тоже.
  В комментариях и статьях базы знаний ссылки рендерятся кликабельными (markdown-рендер превращает
  `vector://…` в кнопку-чип с шифром объекта из кэша).
- **Почта/чат**: ссылку можно вставить в письмо коллеге — у того она откроется в его клиенте через палитру
  (объект у него в кэше или придёт при синхронизации; если объекта нет и связи нет — честное сообщение).

UI-тестами и записью в decision-log.
