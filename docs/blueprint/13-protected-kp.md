# 13. Защищённый выпуск КП — статус NO-GO

> **NO-GO** до отдельного доказательства и утверждённой capability. Ни один элемент среза 1 не реализует
> защищённый выпуск. Согласование ТКП и «регистрация отправки» в срезе 1 — внутренние бизнес-записи, а не
> защищённая выдача байтов. Вендор/продукт (etcd и т.п.) заранее не выбирается.

## 1. Что именно должна доказывать capability

Выпуск разрешает **конкретные byte-identical DOCX bytes** (hash), которые пользователь видел в preview,
и долговечно фиксирует факт выпуска. Он **не** доказывает доставку, прочтение, отсутствие копий/скриншотов.

## 2. Требования к закрытию F-01…F-11 (проектные, без реализации)

| ID | Что закрыть | Проектный подход (гипотеза) | Доказательство для gate |
|---|---|---|---|
| F-01 | Fencing в момент фактического commit, не только на старте | Проверка полномочия, версии ревизии и fencing-токена в той же транзакции, что запись issue; токен монотонен и проверяется хранилищем | Тест: отзыв `deals.editor` между preview и commit → отказ; конкурентный выпуск → ровно один |
| F-02 | Независимо защищённый latest root, идентичность/свежесть | Корень журнала выпусков фиксируется во внешнем независимом свидетеле (решение ИБ); подпись + локальный счётчик недостаточны | Сценарий отката БД к старому снимку обнаруживается |
| F-03 | Все writers в границе либо заблокированы | Права БД: запись в таблицы выпусков — только учётка доверенного сервиса; DDL запрещён; инвентаризация путей записи | Отчёт инвентаризации; попытка прямой записи отклоняется СУБД |
| F-04 | Crash gaps artifact/write/durable/issue/record | Журнал шагов с идемпотентными переходами; recovery различает «не начато / артефакт есть, issue нет / issue есть» без двусмысленности | kill на каждом шаге → детерминированный исход или явный UNKNOWN |
| F-05 | Retry не возвращает DOCX по статусу | Повторная выдача = новая операция с новым ID и всеми текущими проверками; неоднозначный replay без полного свежего журнала = UNKNOWN и блокировка | Тест повтора после обрыва |
| F-06 | Запись issue ≠ доставка; отзыв переданного невозможен | Политика до/во время передачи — решение бизнеса и ИБ (открыто) | Утверждённая политика |
| F-07 | Доказательство успешности DB commit, неопределённый результат | Проверка по operation ID после обрыва (как в эталоне D-12) + сверка с внешним корнем | Тест «commit неизвестен» |
| F-08 | Неизменность принятого артефакта | Артефакт сохраняется до показа; после показа или при неизвестном исходе — **не регенерировать** | hash артефакта = hash preview = hash issue |
| F-09 | Preview = те же точные байты | Preview рендерится из сохранённого артефакта по hash | Тест сравнения байтов |
| F-10 | Bootstrap, identity endpoint/root, replay, восстановление | Процедура первичной инициализации с участием ИБ; защита от повторного bootstrap (эталон: `bootstrap_admin` отказывает при наличии пользователей — только аналог для учёток) | Регламент + тест |
| F-11 | Нет обхода через старые export/reprint/DB/file пути | В новом продукте такие пути не создаются; при миграции — инвентаризация и блокировка | Отчёт |

## 3. Клиентское подтверждение

Действующий пользователь с актуальным `deals.editor` (проверка на сервере в момент эффекта), после
preview точных байтов; чекбокс подтверждения изначально **выключен**. HMAC-ключ — только у доверенного
сервиса в защищённом системном хранилище; без fallback на desktop/DB/AI/env. Клиентская ревизия и
артефакт — отдельные сущности (`KPRevision.settings_json` не считается клиентской ревизией).

## 4. Общие принципы

Fail-closed при неизвестной свежести, identity, истории или состоянии — без fallback. Эта capability
не закрывает общую безопасность ECO/ECR/QMS/AI JSON.
