# 07. Административный центр конфигурации и его строгие границы

> Статус: **спроектировано**. В срезе 1 правила/workflow — версионируемые контракты в репозитории (`/contracts`), а не runtime-настройки.

## 1. Что настраивается без выпуска новой версии

| Группа | Примеры | Scope |
|---|---|---|
| Справочники и каталоги | Единицы, категории позиций, причины отказа, каналы отправки | company / department |
| Допустимые статусы и маршруты согласования | Дополнительный шаг согласования ТКП, обязательность «нет открытых замечаний» | company / project |
| Шаблоны | Документы, отчёты, акты, цифровые паспорта (версионируются; опубликованный шаблон неизменен) | company / project |
| Поля, подписи, представления таблиц | Видимость колонок, порядок, сохранённые фильтры | role / user |
| Видимость элементов | Скрыть неиспользуемые разделы **в рамках существующих прав** | role / user |
| Уведомления и сроки | Напоминание за N дней до срока тендера (N задаёт admin; умолчаний нет) | company / project / user |
| Правила автоматизации из разрешённого списка | Пополнение расходников (вкл./выкл., порог по позиции) | company / warehouse |
| Терминология | «Наряд» ↔ «Производственное задание» | company |
| Интеграции | Адреса, mapping 1С; секреты — «задан/не задан», ввод только на сервере | company |
| Отображение | Тема (светлая/тёмная пастельная), плотность, масштаб, анимации вкл./выкл. | user |

## 2. Приоритет scope

`user` > `role` > `project` > `department` > `company` > *встроенное значение продукта*.

Исключения (ужесточение побеждает): для правил безопасности и согласования действует **наиболее
строгое** значение из всех применимых scope (например, проект может *добавить* шаг согласования, но не убрать шаг компании).
Пользовательский scope доступен только для отображения и персональных уведомлений.

## 3. Жизненный цикл изменения

`draft → validated → preview → published → superseded`

1. **Черновик** — admin редактирует (у accountant — чтение разрешённых групп).
2. **Проверка** — схема, ссылки, противоречия, недопустимые значения (например, порог с >4 знаками, неизвестная единица).
3. **Предпросмотр** — «что изменится»: какие объекты/пользователи затронуты, примеры до/после.
4. **Публикация** — новая версия с автором, временем, причиной; клиенты получают при синхронизации; офлайн-клиент помечает «настройки на версию N».
5. **Rollback** — публикация предыдущего содержимого как *новой* версии (история не переписывается).
Каждый шаг — запись в журнале.

## 4. Строгие границы (конфигурация НЕ может)

* Выполнять произвольный код, скрипты, SQL/массовый DML, скрытые действия.
* Расширять права сверх матрицы `04-permissions.md` или обходить серверную проверку (RBAC).
* Отключать: точность денег/количеств, историю/журнал, обязательные подтверждения (две стороны при пополнении), fencing, разделение обязанностей, NO-GO защищённого КП.
* Подставлять пороги, суммы, ставки, валюты, налоговые правила, округление по умолчанию без источника (Q2, Q8).
* Менять смысл уже опубликованных документов/шаблонов задним числом.
* Включать AI-провайдера без решения admin и без отображения политики приватности.

## 5. Модель данных

`ConfigItem(key, group, schema)` · `ConfigVersion(item, scope_type, scope_id, value_json, version, status, author, reason, created_at, published_at)` · журнал в `audit`.
Значение по умолчанию у продукта для бизнес-параметров — **«не задано»**, и функция, которой нужен параметр, показывает «не настроено — обратитесь к администратору», а не работает на выдуманном значении.
