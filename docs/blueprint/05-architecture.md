# 05. Архитектура: Windows desktop, on-premises сервер, локальное хранилище, синхронизация, интеграции

> Статус: **спроектировано**. Модель синхронизации и границы прав проверены эталоном (Class A).
> Конкретные фреймворки — гипотеза до spikes (09-technology.md).

## 1. Общая схема

```
 Рабочее место (Windows)                                 Инфраструктура компании (on-premises)
┌────────────────────────────────────────┐   TLS (mTLS   ┌──────────────────────────────────────────────┐
│ ВЕКТОР Desktop (нативный UI, без        │   устройства │ ВЕКТОР Application Server (модульный монолит)│
│ WebView/браузера)                       │   — OQ-03)   │  API gateway: аутентификация, версия API     │
│  ├ Shell: навигация, роли-подсказки,    │◀────────────▶│  Application services модулей (03)           │
│  │  темы, DPI, справка                  │  команды /   │  Authz (действие×объект×контекст)            │
│  ├ Модули экранов                       │  запросы /   │  Audit + Operation store (идемпотентность)   │
│  ├ Command bus → Outbox                 │  pull        │  Sync endpoint (push ops / pull changes)     │
│  ├ Local store (шифр., DPAPI-ключ)      │              │  Workers: outbox 1С, уведомления, индексация │
│  ├ File cache / WIP-копии               │              │  File service (CAS по SHA-256)               │
│  └ CAD bridge (named pipe, токен пары)  │              ├──────────────┬──────────────┬────────────────┤
└──────────────┬──────────────────────────┘              │ Server DB    │ File store   │ Secret store   │
               │ локальный pipe                          │ PostgreSQL / │ (файловый    │ (ОС-хранилище/ │
       ┌───────▼────────┐                                │ MS SQL — OQ5)│ ресурс — OQ6)│  HSM — OQ-16)  │
       │ nanoCAD/КОМПАС │                                └──────────────┴──────────────┴────────────────┘
       │ плагин (DLL)   │                                       │ адаптеры (только сервер)
       └────────────────┘                                ┌──────▼──────┐  ┌──────────┐  ┌──────────────┐
                                                         │ 1С (обмен)  │  │ SMTP/IMAP│  │ AI (выкл.)   │
                                                         └─────────────┘  └──────────┘  └──────────────┘
```

Ключевые правила:
* Клиент **никогда** не подключается к серверной БД или файловому хранилищу напрямую; файлы — через File service (поток с проверкой hash).
* Серверный API — транспорт и граница бизнес-правил, а не пользовательский веб-интерфейс.
* Интеграции (1С, почта, AI) — только на сервере, через адаптеры с журналом; секреты — только в серверном хранилище секретов.

|---|---|---|

## 3. Сервер

* **Модульный монолит** (D-04): один процесс/развёртывание, модули с явными интерфейсами; разделение на сервисы — только при измеримой причине (нагрузка, независимый релиз, изоляция безопасности).
* **Единица работы команды**: одна транзакция БД = auth (сеанс) → authz → проверка версии/состояния → эффект → audit → запись результата операции (эталон: `server.py` `_command`). Это даёт fencing в пределах одной БД: отзыв роли сериализуется с эффектом.
* **Идемпотентность**: `operations(operation_id, user, request_hash, response)`; повтор → сохранённый ответ; тот же id + другие данные → отказ; внутренняя ошибка → ничего не записано, повтор безопасен.
* **Неопределённый исход** (обрыв после отправки): клиент повторяет тот же `operation_id` и получает фактический исход; новый id = новая операция.
* **Деньги**: NUMERIC(18,4) на сервере, decimal-строки в API (контракт `money-vectors`).
* **Аутентификация**: гипотеза — интеграция с доменом компании (Kerberos/AD) или собственные учётные записи; решение OQ-03. В эталоне — PBKDF2 и токен сеанса (хранится только SHA-256 токена).

## 4. Синхронизация (проверено эталоном Class A)

```
Клиент                                         Сервер
 execute(cmd) ─ catalog ─┬─ online_required ─▶ офлайн? → отказ «не выполнено, не в очереди»
                         │                     онлайн → сначала досинхронизировать очередь → отправить
                         └─ queued ─▶ outbox(op_id, payload, expected_version) + локальный оверлей «не синхронизировано»
 sync(): по порядку ─▶ command(op_id) ─▶ accepted / replayed  → кэш = ответ сервера
                                      ─▶ conflict (current)   → стоп, показать «моё / на сервере»
                                      ─▶ rejected / denied    → стоп, показать причину
                                      ─▶ нет ответа           → стоп, операция остаётся (тот же op_id)
 pull(): объекты, разрешённые на чтение сейчас (права могли сузиться → кэш очищается)
```

* Идентификаторы новых объектов генерирует клиент (UUID) — без переназначения id после синхронизации (D-05).
* Очередь останавливается на первом конфликте/отказе, чтобы не нарушать причинность (D-06). Улучшение (граф зависимостей по объектам) — после пилота.
* Конфликт **никогда** не сливается автоматически для денег, резервов, согласований, прав, файлов. Пользователь выбирает «Отменить моё» или «Повторить поверх текущей версии» (новая операция).
* Чтение офлайн показывает время последней синхронизации и пометку «не синхронизировано».

## 5. Файлы и перенос (спроектировано; spike S5)

* Хранилище с адресацией по содержимому (SHA-256): blob неизменен; версии документа ссылаются на hash.
* **Перенос** (R-10): задание `FileMoveJob` с одобрением РП → preview (список файлов, размеры, конфликты имён, права цели) → копирование во временное имя → fsync → проверка hash каждого файла → атомарное переименование → обновление ссылок в БД одной транзакцией → `completed` → отдельный шаг удаления источника после повторной проверки. Журнал шагов позволяет восстановление после сбоя на любом шаге (crash между ФС и БД: задание «зависло» → процедура reconcile сравнивает hash и состояние БД, без угадывания).
* Смена системной привязки (какой проект «видит» документ) — отдельная операция, файлы не трогает.

## 7. Безопасность и границы доверия

| Уровень | Защищает от | Не защищает от |
|---|---|---|
| ОС/сеть (ACL, сегментация, TLS) | Посторонних в сети | Администратора домена/сервера |
| БД (учётка сервиса, без доступа клиентов) | Прямых записей пользователей | DBA, который может править таблицы, откатывать журнал |
| Приложение (authz в транзакции, журнал) | Пользователей приложения вне их прав | Изменений в обход приложения (F-03) |
| Журнал append-only (триггеры) | Случайной правки через приложение | Администратора БД: это **не** независимая защита от отката |

* Секреты (пароли интеграций, HMAC-ключи) — только в серверном хранилище секретов; в UI показывается «задан / не задан / дата смены»; в журналы не пишутся (тест `test_no_secrets_in_audit`).
* Локальные данные клиента — шифруются ключом, защищённым DPAPI профиля пользователя; при отзыве устройства сервер отказывает в синхронизации (device revoke — срез 2).

## 8. Развёртывание

* Сервер: служба Windows или Linux-хост (решение по инфраструктуре компании — OQ-05/06), БД, файловое хранилище, резервное копирование (БД + файлы согласованно: снимок БД + манифест hash).
* Клиент: подписанный установщик, обновление с сервера компании, проверка подписи перед установкой.
* Окружения: dev → test (synthetic) → pilot (тестовые данные) → prod (только после gates, 10-roadmap).
