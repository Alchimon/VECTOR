# Резервное копирование и восстановление ВЕКТОР

> Для администратора. Версия документа соответствует коду `0.2.0.dev0` (формат копии `.vbak` v1, схема БД v3).
> ✅ — выполнено по этому документу в Linux-песочнице (SQLite и PostgreSQL 16); 🟡 — не проверено на этой платформе.

## 1. Что входит в копию и что — нет

| Входит (одним файлом `.vbak`) | НЕ входит — копируйте отдельно |
|---|---|
| Все таблицы БД: заказчики, тендеры, ТКП, проекты, комплекты, задачи, документы | Файл конфигурации `/etc/vector/vector-server.toml` |
| **Файлы версий документов** (они хранятся в БД, D-20) | TLS-сертификат и закрытый ключ сервера |
| Учётные записи (хэши паролей Argon2id), роли и история их выдачи | Строка подключения к БД (`vector.env`) |
| Журнал аудита | **Ключ резервных копий** — хранится отдельно по определению (§2) |

Копия содержит персональные данные и хэши паролей, поэтому она **всегда зашифрована** (AES-256-GCM по блокам
с проверкой подлинности каждого блока); незашифрованные копии программа не создаёт.

## 2. Ключ резервных копий ✅

Есть два способа защиты копии; рекомендуется **файл ключа**.

```bash
sudo -u vector /opt/vector/venv/bin/vector-server gen-backup-key /etc/vector/backup.key
# Ключ создан: /etc/vector/backup.key (отпечаток 44715567a203c5f9). Храните копию ключа отдельно…
sudo chmod 400 /etc/vector/backup.key
```

* **Без ключа восстановление невозможно** — ни разработчик, ни поставщик его не восстановят.
* Сразу сделайте **две копии ключа вне сервера**, например: сейф (носитель в конверте) и хранилище
  паролей ИБ. Запишите отпечаток ключа — по нему видно, подходит ли ключ к копии.
* Ключ не храните рядом с копиями: копия + ключ в одном месте = незашифрованная копия.
* Перезаписать существующий файл ключа программа не даст (защита от случайной потери).
* Альтернатива — парольная фраза не короче 16 символов в переменной `VECTOR_BACKUP_PASSPHRASE`
  (или интерактивный ввод). Удобно для ручных копий, неудобно для расписания.

## 3. Создание копии ✅

```bash
sudo -u vector env $(sudo cat /etc/vector/vector.env) /opt/vector/venv/bin/vector-server backup \
  --config /etc/vector/vector-server.toml --key-file /etc/vector/backup.key
# Резервная копия: /var/lib/vector/backups/vector-20261116T123021Z.vbak (2246 байт); строк: 6
# Проверка копии: OK
```

Что происходит:

1. Снимок БД в одной транзакции (PostgreSQL — REPEATABLE READ только чтение, работе пользователей не мешает;
   MS SQL — SERIALIZABLE, запись ждёт окончания копирования 🟡; SQLite — блокировка записи на время копии).
2. Таблицы читаются потоком, запись идёт во временный файл `*.partial`, затем `fsync` и атомарное
   переименование: недописанный файл никогда не выглядит готовой копией.
3. Сразу после записи копия **расшифровывается и проверяется** (число строк и контрольные суммы каждой таблицы).
4. Удаляются старые **автоматические** копии сверх `backup.keep` — только файлы с именем вида
   `vector-20261116T123021Z.vbak`, порядок — по метке времени в имени. Копия, сделанная вручную под
   другим именем (`--out перед-обновлением.vbak`), ротацией не удаляется — её удаляют вручную.

Код выхода: `0` — копия создана и проверена; `2` — копия создана, но проверка не пройдена; `1` — ошибка
(текст в выводе). Существующий файл копии не перезаписывается.

## 4. Расписание и хранение

### Linux (systemd) ✅ синтаксис

`deploy/systemd/vector-backup.timer` запускает копию каждый день в 02:30; если сервер был выключен,
копия будет сделана после включения (`Persistent=yes`).

```bash
sudo systemctl enable --now vector-backup.timer
systemctl list-timers vector-backup.timer
systemctl status vector-backup.service     # результат последнего запуска
```

### Windows (Планировщик заданий) 🟡 не проверено

```powershell
$action  = New-ScheduledTaskAction -Execute "C:\VECTOR\venv\Scripts\vector-server.exe" `
           -Argument 'backup --config C:\ProgramData\Vector\vector-server.toml --key-file C:\ProgramData\Vector\backup.key'
$trigger = New-ScheduledTaskTrigger -Daily -At 02:30
Register-ScheduledTask -TaskName "VECTOR backup" -Action $action -Trigger $trigger `
           -User "<учётная запись службы>" -Password "<пароль>" -RunLevel Limited
```

Переменная `VECTOR_DB_URL` должна быть задана для учётной записи службы (переменные среды пользователя),
ACL на ключ и каталог копий — только эта учётная запись и администраторы.

### Правило 3-2-1

Копии в `/var/lib/vector/backups` защищают от ошибок и порчи данных, но **не от потери сервера**.
Настройте ежедневное копирование файлов `*.vbak` на другой носитель/площадку (сетевое хранилище с
версионированием, лента, отдельная площадка) штатными средствами компании. Копии зашифрованы, поэтому их
можно хранить на общем хранилище — но **без ключа рядом**.

Сколько хранить (`backup.keep`, по умолчанию 14 ежедневных) — решение владельца данных и ИБ; программа
лишь удаляет локальные копии сверх этого числа.

### Контроль

Отсутствие ошибки ≠ наличие копии. Настройте оповещение, если:

* `vector-backup.service` завершился с кодом ≠ 0 (`systemctl --failed`, `OnFailure=` или система мониторинга);
* самой свежей копии в каталоге больше 26 часов.

## 5. Проверка копии ✅

Проверить любую копию можно в любой момент, не трогая БД:

```bash
/opt/vector/venv/bin/vector-server verify-backup /var/lib/vector/backups/vector-20261116T123021Z.vbak \
  --key-file /etc/vector/backup.key
# Создана: 2026-11-16T12:30:21Z · версия 0.2.0.dev0 · схема v3 · источник postgresql
#   customers: …
# Результат: OK
```

Проверка расшифровывает копию потоком (память не зависит от размера) и обнаруживает: неверный ключ,
изменение любого байта, перестановку/удаление/дублирование блоков, обрезку файла, лишние данные в конце.

Понятные ошибки (дословно):

| Ситуация | Сообщение |
|---|---|
| Указан не тот файл (например, сертификат) | «… — не файл ключа резервных копий ВЕКТОР (ожидается одна строка base64). Возможно, указан другой файл…» |
| Ключ от другой установки | «Файл ключа не подходит к этой резервной копии (отпечаток не совпадает).» |
| Копия по ключу, а задана фраза | «Копия зашифрована файлом ключа — укажите --key-file.» |
| Файл оборван | «Файл обрезан.» / «Нет завершающего блока — файл обрезан.» |

## 6. Восстановление ✅

Восстановление выполняется **только в пустую БД** — перезаписать работающую базу невозможно.
Можно восстанавливать в СУБД другого типа (PostgreSQL ↔ MS SQL ↔ SQLite) — например, при переезде.

1. Остановите сервер: `sudo systemctl stop vector-server`.
2. Создайте **новую пустую** базу (§3 [install.md](install.md)); старую не удаляйте, пока не убедитесь в результате.
3. Восстановите (строка подключения к целевой базе — в переменной, не в аргументах):

   ```bash
   sudo -u vector env VECTOR_RESTORE_DB_URL='postgresql+psycopg2://vector:…@db-host:5432/vector_restored' \
     /opt/vector/venv/bin/vector-server restore /путь/vector-20261116T123021Z.vbak --key-file /etc/vector/backup.key
   # Восстановлено строк: 8
   # Сверка: OK — БД готова к запуску
   ```

   Программа: проверяет копию целиком → создаёт схему → ставит метку «восстановление не завершено» →
   вставляет строки в **одной транзакции** → пересчитывает контрольные суммы из целевой БД и сверяет с копией →
   только при совпадении снимает метку.
4. Направьте сервер на восстановленную базу (`VECTOR_DB_URL` в `vector.env`), выполните `vector-server check`
   и запустите службу.
5. Сообщите пользователям: изменения, сделанные после момента копии, утрачены на сервере; неотправленные
   офлайн-изменения клиентов будут отправлены и проверены сервером (по версиям — возможны конфликты,
   их решает пользователь, ничего не сливается молча).

Если что-то пошло не так:

| Ситуация | Что будет |
|---|---|
| Целевая БД не пуста | «Целевая БД не пуста. Восстановление выполняется только в пустую БД», ничего не изменено |
| Копия повреждена / подменена | Отказ до вставки данных; если подмена случилась во время восстановления — транзакция откатывается |
| Сверка не сошлась | Метка «восстановление не завершено» остаётся, **сервер с этой БД не запустится** (fail-closed). Удалите базу и повторите с другой копией |
| Другая версия схемы | «Копия со схемой vN, программа ожидает vM» — восстановите той версией программы, которой сделана копия |

Время: при восстановлении в PostgreSQL на 150 МБ файлов — несколько секунд в песочнице; планируйте по
результатам учебного восстановления ([restore-drill.md](restore-drill.md)), а не по этой цифре.

## 8. Обновление версии программы: миграция схемы ✅ (SQLite, PostgreSQL) · 🟡 MS SQL

Новая версия программы может требовать новую версию схемы БД. Сервер со старой схемой **не запустится**
(`check`/`serve`: «Схема БД v3, программа ожидает v4 … выполните vector-server migrate»). Порядок (D-22):

1. Остановите сервер: `sudo systemctl stop vector-server`. Сделайте обычную копию (§3) — по привычке.
2. Установите новую версию программы.
3. Обновите схему:

   ```bash
   sudo -u vector /opt/vector/venv/bin/vector-server migrate --config /etc/vector/vector-server.toml \
     --key-file /etc/vector/backup.key            # --backup-dir — если не задан [backup] dir
   # Миграция схемы v3 → v4. Сервер должен быть остановлен.
   # Копия до миграции: …/vector-premigrate-v3-20261116T222723Z.vbak — проверена.
   # Создано таблиц: 6 (calc_drafts, …).
   # Готово: схема v4.
   ```

   Пример вывода — для перехода v3 → v4. Текущая версия программы ожидает схему **v6**: из любой версии от v3
   все шаги (v3 → v4 → v5 → v6) выполняются подряд одной командой и одной транзакцией.

   Программа: делает зашифрованную копию **текущей** БД (таблицы её версии схемы) и полностью проверяет её →
   в **одной транзакции** перепроверяет версию, выполняет шаги и записывает новую версию схемы. Сбой на любом
   шаге — откат транзакции, БД остаётся прежней версии. Если схема уже актуальна — «миграция не нужна».
4. `vector-server check` → «Схема БД: v6 — совместима» (номер — текущей версии), запустите службу.

Отказы (ничего не меняется): БД новее программы; нет шага миграции; метка незавершённого восстановления;
таблица, которую миграция должна создать, уже существует (база изменялась вручную — разберитесь до миграции).

**Откат:** восстановите `vector-premigrate-v<N>-*.vbak` в **пустую** БД (§6) той версией программы, которой
работали до обновления, и направьте сервер на неё. Изменения после миграции при этом теряются.

Проверено (Class A, 2026-11-16): `tests/server/test_migrate.py` (SQLite и PostgreSQL 16: данные сохраняются,
копия до миграции восстанавливается, сбой посередине → БД v3 без новых таблиц, отказы), `test_cli_ops.py`;
реальное обновление тестового стенда Linux v3 → v4 скриптом `update-test-stand.sh`. MS SQL — не проверено (#3).
