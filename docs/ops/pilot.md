# План пилота ВЕКТОР

Короткий рабочий документ для владельца: что считаем пилотом, что просим сделать и по каким признакам
решим, что пилот прошёл. Настройки и сроки — ориентиры, их меняет владелец.

## 1. Цель пилота

Проверить на реальных рабочих местах компании то, что в песочнице разработки проверить нельзя:
Windows 10/11 на компьютерах сотрудников, реальная локальная сеть, реальные привычки пользователей
(офлайн-работа, забытый «Завершить», конфликты правок). Пилот — на демо-данных или на копии боевых
данных; решение о продуктивном запуске — отдельное и после пилота.

## 2. Что делает владелец (шаги)

1. **Поставить тестовый стенд** на своём ПК по [test-pc.md](test-pc.md) § 2–5 (~15 минут, Windows).
   Отметка 🟡 в § 4 снимается именно этим запуском.
2. **Прогнать сценарии приёмки** — чек-лист § 6 (П-1…П-28), отмечая ✅ / ❌ / ❓ по ходу.
   Автоматическую самопроверку (`check-stand.cmd`) прогнать до и после ручных сценариев.
3. **Сетевой тест** (по желанию, § 7): сервер на одном ПК, клиенты на двух других — офлайн-очередь
   и конфликт правок двух клиентов.
4. **Собрать замечания** — по § 9 (задача на GitHub, что прислать). Просим прислать даже «всё понятно»:
   это тоже результат пилота.
5. **Заполнить протокол** — § 4 этого документа (копия в задаче пилота).

Ориентировочный срок прогона: 1–2 недели, чтобы сценарии прошли разные люди в разные дни
(учёт рабочего времени живёт в днях и неделях).

## 3. Критерии успеха пилота

Пилот считается пройденным, когда:

* стенд встал на ПК владельца без помощи разработчика (или все места, где понадобилась помощь,
  записаны — это правки инструкции);
* сценарии П-1…П-28 пройдены; критических ❌ (потеря данных, молчаливая перезапись, обход прав)
  нет — непонятности (❓) превращены либо в правки текста, либо в задачи;
* резервная копия снята и учебное восстановление пройдено на ПК владельца
  (по [restore-drill.md](restore-drill.md), строка в его журнале);
* получен ответ на вопросы, блокирующие backlog: подтверждения по blueprint 51
  (выгрузка/квитанция 1С, двойной учёт ст. 153, повышенный лимит по соглашению) —
  без них эти пункты не разрабатываются.

После этого решением владельца начинается этап 8 (адаптеры: файловая проекция, CAD SDK, почта, ACRS) —
порядок и состав адаптеров задаёт владелец.

## 4. Протокол пилота (заполняет владелец)

| Пункт | Результат |
|---|---|
| Дата и состав участников (кто прогонял сценарии) | |
| Версия/коммит пакета (из § 3 test-pc.md или о защите «О программе») | |
| Установка стенда (время, что помешало) | |
| Чек-лист П-1…П-28: ✅ / ❌ / ❓ (ссылки на задачи) | |
| Сетевой тест (делали/нет, результат) | |
| Копия + учебное восстановление (дата, результат) | |
| Ответы по blueprint 51 (1С, ст. 153, лимит) | |
| Решение: этап 8 (какие адаптеры, в каком порядке) | |

## 5. Что делает разработчик во время пилота

* Разбирает задачи из § 9 test-pc.md, отвечает в них же; исправления приходят обновлением стенда
  (§ 7а — данные сохраняются, миграция с проверенной копией).
* Не меняет основания пилота молча: каждая правка — коммит с номером решения (D-NN) и строка
  в decision-log, крупное — дополнение этого плана по согласованию с владельцем.
