## 1. Как устроена система

```
 Рабочие места (Windows)                     Сервер компании (on-prem)                 СУБД
 ┌─────────────────────────┐   HTTPS/TLS    ┌──────────────────────────────┐   SQL    ┌──────────────┐
 │ Клиент ВЕКТОР (Qt/QML)  │ ─────────────▶ │ vector-server (uvicorn)      │ ───────▶ │ PostgreSQL   │
 │ зашифрованный локальный │  /api/v1/...   │ проверка прав, состояний,    │          │ или MS SQL   │
 │ кэш + очередь операций  │ ◀───────────── │ версий; журнал аудита; файлы │          │ (SQLite —    │
 └─────────────────────────┘                └──────────────────────────────┘          │ тест/пилот)  │
                                                         │ vector-server backup        └──────────────┘
                                                         ▼
                                              зашифрованные копии *.vbak
```

* **Клиенты никогда не подключаются к БД напрямую** — только к серверу по HTTPS. Учётная запись БД известна
  только серверу.
* **Сервер — источник истины.** Каждая команда клиента заново проверяется в транзакции: права (по действующим
  выдачам ролей и назначениям), статус объекта, версия, бизнес-правила. Офлайн-изменения клиента — это
  предложения, а не факты.
* **Всё в одной БД**: данные, журнал аудита (только добавление — изменение и удаление запрещены триггерами),
  файлы версий документов (блоками по 1 МБ, с SHA-256). Поэтому одна согласованная копия БД = вся система.
* Поддерживаемые СУБД: **PostgreSQL** ✅ и **MS SQL Server** 🟡 (обязательны по решению владельца;
  MS SQL пока не проверен на настоящем сервере — issue #3). **SQLite** — только тестовый стенд и пилот на одном ПК.

Подробности архитектуры для разработчиков — [architecture.md](architecture.md).

## 2. Требования

См. [install.md, § 2](../ops/install.md#2-требования). Кратко: сервер Linux (проверено) или Windows Server 🟡,
Python 3.11–3.14, PostgreSQL 14+ или MS SQL 2019+ 🟡, сертификат TLS от CA компании; клиент — Windows 10/11 x64.

Диск: БД растёт вместе с файлами документов (каждая версия хранится целиком; одинаковые блоки не дублируются).
Для копий нужен отдельный том/хранилище не меньше размера БД × число хранимых копий (по умолчанию 14).
Во время передачи файла сервер использует системный каталог временных файлов — нужен запас не меньше
`max_file_mb` на каждую одновременную загрузку.

## 3. Установка

| Что | Инструкция |
|---|---|
| Быстрый тестовый стенд на одном ПК (Windows/Linux, демо-данные) | [test-pc.md](../ops/test-pc.md) |
| Рабочая установка: СУБД, учётная запись службы, программа, systemd | [install.md, § 3–6](../ops/install.md) |
| Сервер на Windows | [install.md, § 7](../ops/install.md#7-сервер-на-windows---) 🟡 |
| Рабочие места | [install.md, § 8](../ops/install.md#8-клиент-рабочие-места) и § 12 ниже |

Порядок первой установки (Linux, PostgreSQL):

1. Создать БД и пользователя БД с правами только на свою базу.
2. Создать учётную запись службы `vector` без входа в систему и каталоги `/etc/vector`, `/var/lib/vector`.
3. Установить программу в отдельное виртуальное окружение `/opt/vector/venv`.
4. Положить конфигурацию (§ 4) и секреты (§ 5).
5. `vector-server init` — создаёт схему **только в пустой** БД и первого администратора (пароль спрашивается без эха).
6. `vector-server gen-backup-key` — ключ резервных копий; сразу сохранить его копию отдельно от копий данных.
7. `vector-server check` → `serve` через systemd (`deploy/systemd/vector-server.service`).
8. Включить ежедневную копию: `deploy/systemd/vector-backup.timer`.
9. Сделать первую копию и **учебное восстановление** ([restore-drill.md](../ops/restore-drill.md)).

## 4. Конфигурация

Файл TOML (например, `/etc/vector/vector-server.toml`). Полный пример с пояснениями —
[`config/vector-server.example.toml`](../../config/vector-server.example.toml). **Секретов в нём нет**: сервер
откажется запускаться, если найдёт в файле `database.url`.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `[server] host` | `0.0.0.0` | Адрес прослушивания (`127.0.0.1` — только с этого компьютера) |
| `[server] port` | `8443` | Порт HTTPS |
| `[server] tls_cert`, `tls_key` | — (обязательны) | Цепочка сертификата сервера и закрытый ключ (права 600) |
| `[server] dev_insecure_localhost` | `false` | Только разработка: без TLS и только на 127.0.0.1 |
| `[database] url_env` | — | Имя переменной окружения со строкой подключения (например, `VECTOR_DB_URL`) |
| `[database] url_file` | — | Или файл с одной строкой подключения (права 600 / ACL службы) |
| `[security] password_min_length` | `12` | Минимальная длина пароля (не меньше 8) |
| `[security] lockout_threshold` | `5` | Неудачных входов подряд до блокировки |
| `[security] lockout_minutes` | `15` | Длительность блокировки |
| `[security] session_idle_minutes` | `120` | Сеанс без активности |
| `[security] session_absolute_hours` | `12` | Максимальная длительность сеанса |
| `[security] login_rate_per_minute_per_addr` | `20` | Ограничение частоты попыток входа с одного адреса |
| `[security] max_file_mb` | `200` | Предел размера одного файла версии документа (1…2048 МБ) |
| `[backup] dir` | — | Каталог зашифрованных копий |
| `[backup] keep` | — | Сколько последних автоматических копий хранить |

Значения `[security]` по умолчанию — технические и консервативные, но **не утверждённая политика ИБ компании**
(OQ-18, OQ-20). Сервер не даст задать заведомо опасные значения (пароль короче 8, нулевые сроки).
Строки подключения: PostgreSQL `postgresql+psycopg2://vector:<пароль>@db-host:5432/vector`; MS SQL
`mssql+pyodbc://vector:<пароль>@db-host/vector?driver=ODBC+Driver+18+for+SQL+Server&Encrypt=yes`.

После правки конфигурации: `vector-server check --config …`, затем перезапуск службы.

## 5. Секреты и TLS

Принцип: **секреты не в конфигурации и не в командной строке** (её видно в списке процессов). Где что лежит:

| Секрет | Где | Кто читает |
|---|---|---|
| Строка подключения к БД (с паролем) | `/etc/vector/vector.env` (600, root) или `url_file` (600, vector) | служба |
| Закрытый ключ TLS | `/etc/vector/tls/server.key` (600, vector) — сервер проверяет права | служба |
| Ключ резервных копий | `/etc/vector/backup.key` (600) + **копия вне сервера** (сейф, менеджер паролей) | копирование |
| Пароль первого администратора | ввод без эха при `init` (или `VECTOR_ADMIN_PASSWORD` в автоматизации) | — |

TLS: сертификат выдаёт CA компании; в `tls_cert` — сертификат сервера и промежуточные. Для пилота без CA:
`vector-server dev-cert --dir … --host <имя>` — **только пилот**: такой CA нельзя надолго раздавать на рабочие
места. Клиент проверяет сертификат всегда; ошибка проверки — это отказ, а не «офлайн». Пошагово —
[install.md, § 5](../ops/install.md#5-конфигурация-и-секреты-).

## 6. Запуск, остановка, проверка

| Действие | Команда |
|---|---|
| Проверить конфигурацию, права файлов, подключение и версию схемы | `vector-server check --config /etc/vector/vector-server.toml` |
| Запустить / остановить / состояние (systemd) | `systemctl start / stop / status vector-server` |
| Запустить вручную (тест) | `vector-server serve --config …` |
| Проверка снаружи | `curl --cacert ca.pem https://<сервер>:8443/api/v1/health` → `{"status":"ok"}` |
| Версия программы и схемы | `curl --cacert ca.pem https://<сервер>:8443/api/v1/about` |

`check` и `serve` **не запускают** сервер (fail-closed), если: схема БД другой версии; БД после прерванного
восстановления (метка `restore_in_progress`); строка подключения в конфигурации; ключ TLS доступен группе/всем.
Сообщения объясняют, что делать. Все команды CLI — `vector-server --help`.

## 7. Пользователи, роли и доступ

Учётные записи — собственные в ВЕКТОР (без домена; решение владельца). Управление — в клиенте, раздел
**Администрирование** (роль «Администратор»); все действия попадают в журнал аудита с причиной.

* **Роль доступа ≠ должность ≠ подразделение.** Права определяются глобальными ролями (выдаёт администратор) и
  ролями в проекте (назначения: ГИП проекта — только администратор; РП — администратор или ГИП проекта;
  участники — ГИП/РП проекта).
* **Администратор не получает бизнес-прав** автоматически. Если администратору нужно работать с проектами,
  выдайте ему отдельную роль осознанно (лучше — отдельную учётную запись).
* **Отзыв роли действует сразу**, в том числе для изменений, ожидающих в офлайн-очереди у пользователя:
  сервер проверяет права в момент применения. Повторная выдача — новая запись; прежние согласования не «оживают».
* **Гостевого входа нет.** Новому пользователю задаётся временный пароль; при первом входе он обязан его сменить.
* **Блокировка после неудачных входов** (5 подряд → 15 минут; в списке — метка «Блок.») снимается сама, сбросом
  пароля («Сбросить пароль» снимает блокировку и завершает все сеансы) или повторным включением учётной записи
  (отключение + включение тоже обнуляет счётчик). Отдельной кнопки «Разблокировать» пока нет.
* **Отключение учётной записи** сразу завершает её сеансы. Нельзя отключить себя и последнего действующего
  администратора — защита от потери управления системой.
* **Сброс пароля** делает прежнюю локальную копию данных пользователя на его ПК нечитаемой (новый пароль не
  открывает старый ключ). Клиент откладывает её как `local.db.orphaned-<время>` и не отправляет из неё
  изменения. Перед сбросом попросите пользователя синхронизироваться, если возможно.
* **Утеря ноутбука**: «Завершить все сеансы» + сброс пароля. Локальная копия на ноутбуке зашифрована паролем
  пользователя и секретом его учётной записи Windows.

Полная матрица «кто что может» генерируется из контрактов — [reference.md](reference.md).

### Настройки компании

Раздел **Администрирование → Настройки компании** (модель — `docs/blueprint/07-configuration.md`). Сейчас
поддержана область «компания» и одна настройка:

| Ключ | Значения | Если не задано | Решение |
|---|---|---|---|
| `procurement.rematch_reserved_line` — пересопоставление строки потребности, под которую есть резервы | «Запрещено» (`forbid`) / «Снимать действующие резервы» (`release_active`) | «Запрещено» | D-26, A-26 |

* Публикует только администратор (временное предположение A-26), только при связи, с обязательной причиной.
  Каждая публикация — новая **неизменяемая** версия (`config_versions`, триггер запрещает UPDATE/DELETE) и запись
  аудита «было → стало, причина». Откат — опубликовать прежнее значение.
* Настройка **не расширяет права**: при «Снимать действующие резервы» резервы снимаются, только если у закупщика
  есть право снимать резервы (роль «Склад»). Выданное со склада не отменяется никогда.
* Каталог настроек — `contracts/settings.slice1.json`: произвольные ключи и значения сервер не принимает
  (`unknown_setting`, `bad_value`). Новая настройка = изменение контракта и кода, а не ручная запись в БД.
* Два администратора одновременно: второй получит конфликт версий и увидит действующее значение.

## 8. Резервное копирование и восстановление

Всё пошагово — [backup-restore.md](../ops/backup-restore.md); регламент учений — [restore-drill.md](../ops/restore-drill.md).
Главное:

* `vector-server backup` делает **согласованную** зашифрованную копию всей БД (AES-256-GCM, ключ из файла или
  парольной фразы ≥ 16 символов), **сразу проверяет** её и удаляет старые автоматические копии сверх `keep`.
  Копии, названные вручную, ротация не трогает.
* `vector-server verify-backup` — полная проверка подлинности и целостности (число строк и SHA-256 каждой
  таблицы) без восстановления.
* `vector-server restore` — только в **пустую** БД (защита от перезаписи); до успешной сверки сервер на такой
  БД не запустится. Копию PostgreSQL можно восстановить в MS SQL и наоборот.
* **Правило 3-2-1**: три копии, два типа носителей, одна — вне площадки. **Ключ храните отдельно от копий**:
  копия без ключа бесполезна, ключ без копии — тоже. Утрата ключа = утрата всех копий.
* Это дополнение к штатным средствам СУБД (pg_dump/PITR, BACKUP DATABASE), а не их замена.
* Учебное восстановление — не реже раза в квартал и после каждого обновления (A-17).

## 9. Обновление версии программы

Пошагово — [backup-restore.md, § 8](../ops/backup-restore.md#8-обновление-версии-программы-миграция-схемы--sqlite-postgresql---ms-sql);
для тестового стенда — [test-pc.md, § 7а](../ops/test-pc.md). Порядок:

1. Сообщить пользователям, попросить синхронизироваться. Остановить службу.
2. Сделать и проверить обычную копию (по привычке).
3. Установить новую версию в то же окружение.
4. `vector-server migrate --config … --key-file …` — программа сама делает и проверяет копию **текущей** БД, затем
   в **одной транзакции** обновляет схему (v3 → v4 → v5 → v6 → v7). Сбой — откат, БД остаётся прежней.
5. `vector-server check` → запустить службу → проверить `/api/v1/about` и вход.
6. **Откат**: восстановить `vector-premigrate-v<N>-*.vbak` в пустую БД прежней версией программы.

Клиенты: новая версия клиента устанавливается так же, как первая (§ 12). Неотправленная очередь клиента
сохраняется при обновлении клиента.

## 10. Мониторинг и журналы

| Что | Где / как |
|---|---|
| Жив ли сервер | `GET /api/v1/health` (без входа) → `{"status":"ok"}`; удобно для мониторинга (Zabbix, Prometheus blackbox) |
| Версия программы и схемы | `GET /api/v1/about` |
| Журнал сервера | вывод службы: `journalctl -u vector-server` (строки `время УРОВЕНЬ модуль: сообщение`) |
| Журнал копий | `journalctl -u vector-backup`; признак успеха — «Проверка копии: OK» |
| Журнал аудита (кто, когда, что, на каком основании, результат — в том числе отказы в правах) | таблица `audit_log` в БД; в клиенте — блок «История» у каждого объекта |
| Свободное место | каталог копий, том БД, каталог временных файлов |

Что контролировать ежедневно: свежая копия прошла проверку; сервер отвечает на `/health`; нет роста ошибок в
журнале. Пароли, токены и строки подключения в журнал **не пишутся** (строка подключения — только с маской).
Журнал аудита нельзя изменить или очистить средствами приложения и обычными UPDATE/DELETE (триггеры в БД).

## 11. Безопасность

* Только HTTPS; редиректы клиентом не выполняются; сертификат проверяется всегда.
* Пароли — стойкий хэш Argon2id на сервере; блокировка и ограничение частоты входа; сеансы с ограничением по
  бездействию и общему сроку; смена пароля завершает другие сеансы.
* Права проверяются на сервере в момент действия; роль из запроса клиента игнорируется.
* Тело запроса ограничено, размер файла проверяется **до** приёма тела; файл сверяется по SHA-256 при загрузке и
  скачивании.
* Локальные данные клиента зашифрованы (AES-256-GCM); ключ защищён паролем пользователя и секретом устройства в
  диспетчере учётных данных Windows; без защищённого хранилища клиент кэш не создаёт.
* Учётная запись БД сервера — с правами только на свою базу; доступ к порту СУБД — только с сервера ВЕКТОР.
* Сервер: отдельная учётная запись службы без входа, каталоги 700, секреты 600; юнит systemd с ограничениями
  (`deploy/systemd/vector-server.service`).

## 12. Рабочие места

⛔ Установщика (MSI, подпись кода) пока нет — issue #4. Сейчас: виртуальное окружение Python и пакет
`vector[client]` ([install.md, § 8](../ops/install.md#8-клиент-рабочие-места)) или тестовый стенд.

* Выдайте пользователю адрес сервера и, если CA компании не установлен в Windows, файл `ca.pem`.
* Локальные данные: `%LOCALAPPDATA%\VECTOR\profiles\<сервер>\<пользователь>` (зашифрованы). Настройки формы
  входа и тема — в реестре пользователя (QSettings «VECTOR-desktop»). Секрет устройства — в диспетчере учётных
  данных Windows (служба «VECTOR-desktop»).
* Офлайн-вход разрешён 7 дней после последнего входа при связи (OQ-20).
* **Очистка локального кэша** (если клиент сообщает «Локальные данные повреждены»): закрыть клиент, переименовать
  каталог профиля пользователя, войти при связи — кэш создастся заново. Неотправленные изменения из старого
  каталога при этом не отправятся.

## 13. Регламент обслуживания

| Периодичность | Действие |
|---|---|
| Ежедневно | Копия создана и проверена («Проверка копии: OK»); `/health` отвечает; место на дисках |
| Еженедельно | Копия скопирована вне площадки (3-2-1); просмотр журнала сервера на ошибки и отказы входа |
| Ежемесячно | Ревизия учётных записей и ролей (уволенные, лишние права); срок действия сертификата TLS |
| Ежеквартально | Учебное восстановление ([restore-drill.md](../ops/restore-drill.md)) с записью в журнал |
| При обновлении | Копия → `migrate` → `check` → учебное восстановление новой версией |

## 14. Неисправности

| Симптом | Причина | Что делать |
|---|---|---|
| `check`: «Версия схемы БД N не совпадает с версией приложения M» | Обновили программу без миграции (или БД новее) | § 9 (`migrate`); если БД новее — установите соответствующую версию программы |
| «Восстановление … не завершено или не прошло сверку. Запуск остановлен» | Прерванное/неудачное восстановление | Восстановите заново в **новую пустую** БД |
| «Строку подключения нельзя хранить в конфигурации» | `database.url` в TOML | Перенесите в `url_env` / `url_file` (§ 5) |
| «…файл … доступен группе/всем (права …). Установите 600» | Права ключа TLS/секрета | `chmod 600`, владелец — учётная запись службы |
| «База данных не пуста — инициализация отменена» | `init` на существующей БД | Это защита; для новой установки — новая пустая БД |
| Клиент: «Сертификат сервера не прошёл проверку» | Нет CA на ПК, неверное имя в сертификате, подмена | Выдать `ca.pem`; имя сервера в адресе = имя в сертификате |
| Клиент: «Нет связи с сервером» при работающем сервере | Брандмауэр, адрес/порт, сервер слушает 127.0.0.1 | `host = "0.0.0.0"`, правило брандмауэра на порт, `curl /health` с ПК |
| Пользователь заблокирован | 5 неудачных входов | Подождать 15 минут или «Сбросить пароль» |
| «Файл больше допустимого размера» | `max_file_mb` | Увеличить в `[security]` (до 2048) при наличии места |
| Копия: «Файл ключа не подходит к этой резервной копии» | Другой ключ | Найдите ключ с тем же отпечатком (выводится при создании) |
| Копия: «Проверка подлинности не пройдена…» | Копия повреждена/изменена или неверный ключ | Используйте другую копию; проверьте носитель |
| `migrate`: «Таблицы, которые должна создать миграция, уже существуют…» | БД изменялась вручную | Разберитесь до миграции; восстановление из копии |
| Медленные записи во время ночной копии (MS SQL, SQLite) | Копия держит согласованный снимок | Копировать вне рабочего времени |

Сообщение об ошибке разработчикам: версия (`/api/v1/about`), точный текст, время (UTC), фрагмент журнала сервера,
журнал клиента (консольное окно на стенде). Пароли и строки подключения не пересылайте.

## 15. Ограничения текущей версии

* MS SQL Server — не проверен на настоящем сервере (issue #3); Windows Server как платформа сервера — 🟡.
* Нет установщика клиента и подписи кода (issue #4); вид при масштабе Windows 125–150 % не проверен.
* Нет кнопки «Разблокировать» (только сброс пароля / отключение и включение учётной записи).
* Права — временные предположения (A-03…A-24) до подтверждения владельцем; политика паролей и офлайн-срок —
  OQ-18, OQ-20.
* Фактическая себестоимость, перемещения между складами, совместное решение склад+закупка, заказы поставщикам —
  следующие этапы (дорожная карта, этап 4 часть 2).
