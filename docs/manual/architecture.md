# Устройство ВЕКТОР — руководство разработчика

Для кого: разработчик, который будет сопровождать или расширять систему. Документ отвечает на вопросы «где что
лежит», «как проходит команда от кнопки до БД», «как работает офлайн» и «что нельзя сломать». Правила работы
с репозиторием (коммиты, комментарии, что нельзя без владельца) — в [CONTRIBUTING.md](../../CONTRIBUTING.md);
проектная документация (требования, решения) — в [docs/blueprint](../blueprint).

## 1. Технологии и почему

| Слой | Технология | Почему |
|---|---|---|
| Язык | Python 3.11+ (весь код, кроме интерфейса) | Один язык для сервера, клиента и тестов; `Decimal` для денег; зрелые драйверы PostgreSQL и MS SQL |
| Клиент | Qt 6 / QML через PySide6 6.11.x | Нативное приложение Windows без браузера (решение владельца); тема, клавиатура, высокое DPI |
| Сервер | ASGI (Starlette) + uvicorn, TLS | Небольшой внутренний API; никакого веб-интерфейса |
| БД | SQLAlchemy Core (без ORM) | Один код схемы и запросов для PostgreSQL, MS SQL и SQLite; явный SQL без «магии» |
| Криптография | `cryptography` (AES-256-GCM, scrypt), `argon2-cffi` | Шифрование копий и локального кэша, хэши паролей |
| Секреты клиента | `keyring` → диспетчер учётных данных Windows | Секрет устройства не лежит в файле рядом с кэшем |

Ограничение версии PySide6 `>=6.11.3,<6.12` — из-за ошибки счётчика ссылок в 6.12 (D-21).

## 3. Контракты — что можно делать и кому

Три файла в `contracts/` описывают поведение системы декларативно; код обязан им соответствовать:

* `command-catalog.slice1.json` — все команды изменения: класс (`queued` — можно офлайн, `online_required` —
  только при связи), нужна ли `expected_version`, какие поля.
* `permissions.slice1.json` — для каждой команды: какие глобальные роли и роли в проекте её разрешают.
  Правила домена поверх прав (например, «автор последней правки не согласует ТКП сам») проверяются в
  обработчике и описаны в его docstring.
* `workflows.slice1.json` — статусы и разрешённые переходы тендера, ТКП, задачи, документа.

Проверки согласованности при запуске: команда в каталоге без правила прав или без обработчика → `Service`
не создаётся (ошибка запуска, а не «тихо не работает»). `tools/sync_contracts.py --check` — копия в пакете
совпадает с `contracts/`; `tools/gen_manual_ref.py --check` — справочник [reference.md](reference.md)
сгенерирован из текущих контрактов.

## 4. Путь команды: от кнопки до БД

```
QML-кнопка ─▶ Backend (слот, рабочий поток) ─▶ SyncClient.submit(command, payload, expected_version)
                                                   │
             queued и нет связи ◀──────────────────┤ online_required и нет связи → отказ «нужна связь»
             запись в очередь + оптимистичная      │
             правка кэша («Не отправлено»)         ▼
                                       HttpTransport POST /api/v1/command  {operation_id, token, command,
                                                   │                         payload, expected_version}
                                                   ▼
Service._command: проверка конверта → SHA-256 запроса → транзакция:
   1. сеанс (_auth)  2. operation_id уже был? → вернуть сохранённый ответ (повтор безопасен)
   3. SAVEPOINT → обработчик: only_keys → policy.check(project_id) → _require/_check_version/статус → запись
      → ctx.log (основание доступа, версия до/после)
   4. успех: журнал аудита; отказ (Rejected/Denied/Conflict): откат до SAVEPOINT, отказ тоже в журнал
   5. исход → таблица operations (для повторов)                     │
                                                   ◀───────────────┘ {status, result | code+message_ru}
SyncClient: кладёт result в кэш, снимает пометку; Backend: сигнал dataChanged → QML перечитывает модель
```

Важные свойства:

* **Идемпотентность.** `operation_id` (UUID) создаётся один раз при постановке в очередь и не меняется при
  повторах. Повтор с тем же id и теми же данными возвращает прежний ответ (`replayed: true`); с другими
  данными — отказ `operation_id_reused`. Поэтому потерянный ответ (`ResponseLost` → «результат неизвестен»)
  безопасно повторять.
* **Транзакция может выполниться несколько раз** (конфликт сериализации → повтор, до `MAX_ATTEMPTS`).
  Обработчики не должны иметь внешних эффектов вне БД (файлы, сеть, глобальные переменные).
* **Права проверяются в момент эффекта** внутри той же транзакции. Роль из запроса не используется. Для
  проектных объектов обязательно передавать `project_id` в `policy.check`, иначе роли в проекте не учтутся.
* **Версии.** У изменяемых объектов есть `version`; правка передаёт `expected_version`; несовпадение →
  `Conflict` с текущим состоянием, которое клиент показывает в сравнении «моё / на сервере».
* **Журнал аудита** — только добавление (триггеры СУБД запрещают UPDATE/DELETE); у каждой записи есть
  основание доступа (`Authority`: роль/назначение и номер выдачи).

## 5. Офлайн-работа (клиент)

* **Профиль** = пара «сервер + пользователь»: `local.db` (SQLite) в `%LOCALAPPDATA%\VECTOR\profiles\…`.
  Значимые поля зашифрованы по отдельности (AES-256-GCM). Ключ шифрования данных (DEK) хранится в профиле
  завёрнутым ключом KEK = HKDF(scrypt(пароль, соль) ‖ секрет устройства), где секрет устройства лежит в
  диспетчере учётных данных Windows (`vault.py`). Без пароля и без учётной записи Windows кэш не читается.
* **Вход.** При связи — онлайн (сервер проверяет пароль, выдаёт токен, клиент обновляет кэш командой `pull`).
  Без связи — офлайн-разблокировка профиля, если последний онлайн-вход был не раньше 7 дней назад (OQ-20).
* **Очередь** (`sync.py`): только команды `queued`. Синхронизация строго по порядку, каждые 20 с и по `F5`;
  на первом конфликте или отказе — остановка (следующие операции могли зависеть от этой). Пользователь решает:
  отменить своё (`discard`) или применить поверх текущей версии (`reapply_on_current` — та же правка с новой
  `expected_version` и новым `operation_id`). Автоматического слияния нет — решение владельца.
* **Что никогда не уходит в очередь:** согласования, права, деньги в итогах, складские проводки и резервы,
  файлы документов — они `online_required` (D-23 и др.). Складская проводка, ссылающаяся на ещё не
  отправленный склад, блокируется (`blocked`), а не ставится в очередь.
* **Покрытие потребности** локально не пересчитывается — после принятых складских команд клиент делает `pull`.

## 6. Деньги и количества

* Только `Decimal`; в JSON — строки (`"1250.5000"`), никогда float. Не больше 4 знаков после запятой;
  вне диапазона → отказ, а не округление.
* Хранение: PostgreSQL/MS SQL — `NUMERIC(18,4)`; SQLite — BIGINT в десятитысячных.
* Различаются: ноль ≠ пусто ≠ неизвестно ≠ «не применимо» ≠ ошибка. Итог, в который входит неизвестное, —
  «неизвестно», а не сумма известных частей.
* Официальный итог проекта — только из явно зафиксированных версий расчётов комплектов; фиксация создаёт новую
  ревизию итога, история сохраняется.
* Эталонные примеры — `contracts/money-vectors.json`; тесты прогоняют их и на сервере, и в ядре.

| `tests/ui` | QML без экрана (offscreen): навигация, формы, состояния, роли | ~40 с |

```bash
source .venv/bin/activate
export LD_LIBRARY_PATH=$PWD/.venv/stubgl QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software   # для tests/ui
python -m pytest -q tests                      # всё (~3,5 мин)

```

Серверные тесты по умолчанию работают на временной SQLite; на PostgreSQL — через временный локальный сервер
(pgserver). MS SQL в автотестах пока нет (issue #3). Классы тестов (A — песочница, B — стенд, C — реальная
среда только с разрешения) не смешиваются: см. [blueprint, раздел тестирования](../blueprint).

## 9. Как добавить новую команду (чек-лист)

1. **Решение.** Если команда затрагивает права, деньги, статусы или офлайн — запись в Decision Log
   (`docs/blueprint/12-decision-log.md`) с пометкой «временное предположение», если владелец ещё не подтвердил.
2. **Контракты.** Добавить команду в `command-catalog` (класс `queued`/`online_required`, поля), правило в
   `permissions` (роли, условия), при необходимости — статусы в `workflows`. `python tools/sync_contracts.py`.
3. **Схема.** Новая таблица/столбец → повысить `db.SCHEMA_VERSION` и добавить шаг в `migrate.py`
   (тест миграции обязателен). Деньги — тип из `db.py`, не float.
4. **Обработчик** `_xxx_yyy(self, ctx, p, ev)` в нужной примеси по схеме из docstring `Service`:
   `only_keys` → `policy.check(..., project_id=)` → проверки → запись → `ctx.log` → представление. Добавить
   в `Service.handlers`. Подробный docstring: что делает, почему так (ссылка на D-/A-), что с офлайном.
5. **Клиент.** Слот в `backend.py`; для `queued` — оптимистичная правка кэша в `sync.py`; QML — кнопка,
   скрытая без права (это только подсказка), все состояния: пусто, загрузка, ошибка, нет доступа, офлайн.
6. **Тесты:** успех; отказ по праву для каждой неподходящей роли; неверный статус; конфликт версии; повтор с
   тем же `operation_id`; аудит; для офлайна — поведение без связи.
7. **Документация:** `python tools/gen_manual_ref.py`; раздел в [user-guide.md](user-guide.md);
   при изменении интерфейса — снимки экранов; CHANGELOG.

## 10. Инварианты, которые нельзя ломать

* Клиент не ходит в БД; сервер — источник истины; финальные действия перепроверяются на сервере.
* Нет правила — нет доступа (fail-closed). Отзыв роли действует сразу; повторная выдача не «оживляет»
  старые согласования. ГИП назначает только администратор. Гостевого входа нет.
* Журнал аудита и версии файлов неизменяемы (триггеры СУБД). Версия документа — новая запись, а не правка.
* Никаких молчаливых слияний денег, резервов, согласований, прав и файлов.
* Сервер не запускается на БД другой версии схемы или после незавершённого восстановления.
* Секреты не в конфигурации, не в командной строке, не в журнале.
* Не придумывать бизнес-правила (пороги, налоги, валюты, округление) — только с владельцем или как явно
  записанное временное предположение.
