# Как вносить изменения в ВЕКТОР

Документ для разработчиков (людей и ИИ-агентов). Цель — чтобы любое изменение было понятно,
проверяемо и откатываемо, а продукт не «додумывал» бизнес-правила за владельца.

## 1. Ветки и коммиты
- Работа ведётся в рабочей ветке; в `main` — только через pull request и **только по решению владельца**.
- Один коммит — одна законченная мысль: «исправление интерфейса», «команда task.create + тесты», «документация».
  Не смешиваем в одном изменении интерфейс, схему БД, склад и безопасность.
- Сообщение коммита — по-русски, в повелительном наклонении, с областью:
  `server: команды задач проекта`, `ui: реактивные подсказки прав`, `docs: журнал решений D-19`.
  В теле — *зачем*, что проверено и как откатить, если это не очевидно.
- Не переписываем историю опубликованных веток (без force-push / rebase).

## 2. Комментарии в коде — обязательны и подробны
Код читают инженеры компании и аудиторы безопасности, поэтому комментарии объясняют **почему**, а не пересказывают строку.

- **Модуль** начинается с docstring: назначение, границы ответственности, главные инварианты.
- **Функция/класс** с нетривиальной логикой — docstring: что делает, входы/выходы, какие ошибки и в каких случаях.
- **Бизнес-правило** — комментарий со ссылкой на источник: решение `D-xx`, временное предположение `A-xx`,
  требование `R-xx`, правило матрицы прав. Пример:
  ```python
  # Проект создаётся ТОЛЬКО из выигранного тендера и только один (решение владельца, D-03 / R-04).
  # Проверка повторяется на сервере в той же транзакции, что и вставка, — клиенту не доверяем.
  ```
- **Безопасность** — комментарий, от чего защищает конкретная проверка (подбор пароля, повтор операции, утечка в лог…).
- **Деньги/количества** — где квантование, почему Decimal, что считается «пусто» и «ноль».
- **QML** — комментарий у каждого компонента: назначение, публичные свойства, какие состояния
  (пусто / загрузка / ошибка / нет доступа / офлайн / конфликт) он показывает.
- Язык комментариев — русский; идентификаторы — английские.

## 3. Чего нельзя делать без владельца
- Придумывать права, пороги, налоги, валюты, округления, значения по умолчанию, юридический смысл статусов.
  Если без значения нельзя двигаться — записать **временное предположение** в `docs/blueprint/12-decision-log.md`
  (A-xx) так, чтобы его было легко изменить.
- Автоматически сливать конфликтующие изменения денег, согласований, прав, резервов и файлов.
- Хранить секреты в репозитории, конфигурации или журналах (см. `SECURITY.md`).
- Подключать клиент напрямую к СУБД; включать GitHub Actions; работать с реальными БД и 1С из тестов.

## 4. Контракты — источник истины
`contracts/*.json` описывают команды, права, переходы статусов и денежные тест-векторы. После правки:
```bash
python tools/sync_contracts.py          # копирует контракты в пакет (src/vector/core/contracts_data)
python tools/sync_contracts.py --check  # проверка в тестах/перед коммитом
```
Новая команда = запись в каталоге (с офлайн-классом F/Q/O и `label_ru`) + правило в матрице прав +
обработчик на сервере + тесты (разрешено / запрещено / конфликт / повтор / аудит).

## 5. Тесты
Каждое правило — тест, который **падает**, если правило сломать. Перед коммитом:
```bash
python -m pytest -q -p no:cacheprovider tests
(cd spikes/reference-core/tests && python -m unittest)
```
В отчёте указываем точные команды и результаты; пропуски — с причиной. Классы A/B/C не смешиваем.

Поднятие среды разработки с нуля (Linux без GUI: песочница, CI):
```bash
python3.11 -m venv .venv
.venv/bin/pip install -e ".[server,client,dev]" -c deploy/test-stand/constraints.txt
bash tools/make_stubgl.sh   # заглушки GL/EGL/xkbcommon/dbus → .venv/stubgl
```
Клиентские и UI-тесты, стенд снимков: `LD_LIBRARY_PATH=.venv/stubgl QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software`.

Линтер (ruff, входит в `dev`-зависимости; чистый базовый уровень — поддерживаем чистым):
```bash
ruff check src/ tools/ --select F,E9,S,B905,B007
ruff check tests/ --select F,E9 --ignore F811   # F811 — осознанный паттерн: импорт фикстуры из соседнего модуля
```
B904 (raise без `from` в except) не применяем: доменные ошибки намеренно не связывают с внутренними исключениями.

## 6. Интерфейс
- Цвета, размеры, радиусы — только через токены `qml/Theme.qml` (светлая и тёмная темы).
- Тексты — по-русски, без внутренних кодов (`tender.transition` → «Сменить статус тендера»).
- После изменения интерфейса пересоздать скриншоты (`docs/screenshots/README.md`) и просмотреть обе темы.

## 7. Отчёт по шагу
Каждый законченный шаг — отчёт в `docs/blueprint/NN-*.md` в формате раздела 17:
требования · реализовано/спроектировано/заблокировано · файлы и риск отката · команды и результаты ·
проблемы с `файл:строка` · проверенные роли/состояния/офлайн · изменения журнала решений · что нужно от владельца.
Краткая запись — в `CHANGELOG.md`.
